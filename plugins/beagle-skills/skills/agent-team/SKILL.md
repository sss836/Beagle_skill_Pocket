# 多 Agent 指挥官

将用户的实际目标交付完成。主 agent 持有目标和决策权，子 agent 承担明确且有边界的工作。

## 先确定工作契约

从当前对话获取目标、原始输入、交付格式、验收标准、允许修改的范围和已经给出的授权。缺少会改变结果的必要输入时简短询问，同时推进不依赖这些输入的工作。用户只打开技能或询问怎么用时，给一个调用示例并询问任务，不自行选择项目开工。

默认采用 3 个子 agent；用户指定人数时遵从其要求，并按宿主的实际并发限制分批安排，不将“计划创建”说成“已经运行”。宿主没有子 agent 工具时说明限制，再以主 agent 完成可执行部分，明确区分普通检查和独立验收。

## 具体职责

| 角色 | 负责什么 | 必须交付 | 工作边界 |
| --- | --- | --- | --- |
| 主 agent | 拆解、任务派发、依赖安排、方案决策、证据核对、整合交付 | 分工简表、最终成果、实际验证与剩余问题 | 对完整目标负责，不能只转发子 agent 摘要 |
| A：调查与方案 | 检查原始资料、现状、原因和可选方案 | 可定位的发现与证据、建议方案、未解决问题 | 默认只读，不修改 B 的产物 |
| B：实施与产出 | 按确定方案完成实际文件、代码或内容 | 真实产物、变更说明、自查结果 | 只修改明确分配的文件或内容 |
| C：独立验收 | 对照用户目标和原始输入检查实际产物 | 通过项、可复现问题、位置、严重程度和修正建议 | 默认只读；结论来自检查，不以 B 的自评代替验证 |

这些是默认职责，不是所有任务都要经过同一流水线。并行研究或对比任务可将 A、B 改为不同研究方向，保留 C 交叉核查和主 agent 综合判断；纯审阅任务不安排实现；多个互不相交的实现模块可以并行分配。已完成的输入调查不用重做。

## 派发与协作

开始时向用户展示简短分工：谁负责什么、输出什么、哪些工作需要等待。每次派发都给出目标、必要背景、输入位置、负责范围、输出位置、验收条件和依赖。需要专门领域知识时，从当前可用技能中挑选并读取最相关的 `SKILL.md`，将必要技能路径和要求交给对应子 agent；不为凑角色加载所有技能。

使用宿主实际提供的创建、消息、跟进和等待工具。独立工作并行进行，有依赖的部分在前置结果具备后启动；例如 A 调查时 C 可以先整理验收条件，B 的产物具备后再由 C 检查。提前写好的验收清单不算完成了产物验收。

同一文件同时只分配一个写入者。共享工作区中检查已有修改，不覆盖其他人的工作。子 agent 发现跨范围问题时报告主 agent，由主 agent 重新分配。继续使用已有子 agent 跟进修正，避免每个问题都新建角色。

## 检查与修正

主 agent 接收结果后打开产物并检查关键证据。C 从原始输入和验收条件出发独立检查，不向 C 暗示“应该通过”。涉及审稿、盲审等有独立性要求的领域时，遵守相应技能的隔离规则。

将实质性问题交回 B 修正，再请 C 检查受影响部分。通常最多进行两轮聚焦修正；重复遇到同一外部阻塞或必须由用户决定的取舍时，交付已完成部分并明确说明剩余事项，避免无限循环。不需要用户决策的普通实现问题继续解决。

只在实际完成相应检查后声称“通过”。最终给出真实产物位置、主要结果、实际验证、未解决事项；避免展开内部对话记录。委派与技能调用不扩大原任务或外部操作的授权范围。

需要派发格式或特殊任务示例时读取 [分工示例](references/delegation.md)。
